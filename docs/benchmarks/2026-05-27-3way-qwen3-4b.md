# forge vs pegainfer vs vLLM — Qwen3-4B (GB10)

Date: 2026-05-27
Harness: `scripts/bench_openai.py` (single-concurrency, greedy, streaming)
Workload: prompt ~1024 tok, out=256 tok, 5 runs (decode_heavy)
Model: Qwen3-4B FP16 (hidden=2560, 36 layers, 32 heads, 8 KV heads, head_dim=128)
Hardware: NVIDIA GB10 (DGX Spark, Grace-Blackwell, sm_121, ~273 GB/s)

## Result — same-session, back-to-back

All three measured the same day in one session. The GB10 GPU clock is **not
pinned** (208 MHz idle → 2405–3003 MHz under load, ±20% cross-time noise), so
only back-to-back same-session numbers are comparable. Clock stability was
confirmed: pegainfer reproduced its 2026-05-26 numbers (131/46.3) almost
exactly, so today's window matches the earlier baseline.

| engine | config | TTFT (prefill) | TPOT (decode) | decode tok/s |
|--------|--------|----------------|---------------|--------------|
| forge | FA2 + persistent-LSE + decode-upload-skip + **last-token logits**, eager | **131.4 ms** | 58.7 ms | 17.0 |
| forge (before last-token logits) | full-seq logits | 254.7 ms¹ | 58.3 ms | 17.1 |
| pegainfer | CUDA graph (default) | 130.8 ms | **46.0 ms** | **21.7** |
| vLLM (nvcr 26.01) | **enforce-eager**² | **47.8 ms** | 46.5 ms | 21.5 |

The **last-token-logits** fix (prefill computes the LM head only for the final
prompt position instead of all `seq_len` positions — `model.rs` `forward_single`
slices `hidden` to its last row before the head) cut forge TTFT **254.7 → 131.4
ms (−48%)** in a clean back-to-back, output byte-identical (greedy). This closes
the prefill gap to pegainfer entirely (131.4 vs 130.8). TPOT unchanged (the fix
is isolated to prefill). Root cause was a full `[seq_len, vocab]` LM-head matmul
+ a ~622 MB `[1024, 151936]` f32 logits D2H copy (~83 ms) of which the engine
used only the last row.

¹ forge TTFT is noisy: non-outlier runs land 261–291 ms, with occasional
~2.8 s first-token spikes (a separate latency-spike bug worth chasing).
² vLLM's default compiled mode (`torch.compile` + full CUDA-graph capture)
**hangs after flashinfer autotuning** on this GB10 container and never serves;
`--enforce-eager` is the only config that comes up. Default
`gpu_memory_utilization=0.9` also OOMs during sampler warmup → use `0.6` +
`--max-num-seqs 16`. So vLLM's number here is its **eager** path, not its best.

## Interpretation

- **decode (TPOT):** forge 56.9 ms vs pegainfer/vLLM ~46 ms → forge is **~1.24×
  behind**. pegainfer and vLLM are tied. This session's `decode-upload-skip`
  (eliminating redundant per-step H2D of token indices / RoPE cos-sin /
  block_tables / kv_lens) cut forge eager TPOT 85.75 → 57.5 ms (−33%, measured
  via a clean baseline-vs-fixed back-to-back), closing the gap from ~1.5× to
  1.24×.
- **prefill (TTFT):** after the last-token-logits fix, forge **131.4 ms == pegainfer
  130.8 ms** — the 2× gap is gone. Still ~2.7× vLLM's 48 ms, which is
  exceptionally fast. Two fixes landed here: (a) FA2 persistent-LSE (dropping a
  per-layer `cudaMalloc`/`cudaStreamSynchronize`/`cudaFree` of the softmax-LSE
  scratch — 36 serialization barriers per prefill) gave −17%; (b) last-token
  logits gave the big −48% by eliminating the full-sequence LM head + 622 MB
  logits D2H.

## What this points at

After the last-token-logits fix, forge matches pegainfer on prefill and trails
both engines by ~1.27× on decode. The nsys prefill profile that drove the fix
(`transpose_f16` topping the kernel summary was a one-time weight-transpose at
load, captured because model load is inside the nsys window — **not** a
per-prefill cost) showed the real per-prefill waste was the full-sequence LM
head + logits D2H, now eliminated. Remaining headroom:

- **decode 1.27×** (58.7 vs 46 ms) — host/launch-bound, ~280 kernels/step; needs
  kernel fusion or a working decode CUDA-graph (currently a regression on GB10).
  See `docs/benchmarks/2026-05-25-cuda-graph-decode-measurement.md`.
- **prefill vs vLLM 2.7×** (131 vs 48 ms) — likely the same launch/alloc overhead
  (~1452 `cuMemAllocAsync`/prefill); a persistent-buffer prefill path (mirroring
  decode) is the next lever.

## 2026-05-28 update — decode root-cause + same-session refresh

Re-ran forge (current HEAD) vs pegainfer back-to-back in a fresh session. SM
clock was steady at 2411 MHz throughout decode (verified by sampling — the
208 MHz seen via `nvidia-smi -q` earlier was the GPU fully idle *before* the
server started; a running server holds it at 2411).

| engine | TTFT (prefill) | TPOT (decode) | decode tok/s |
|--------|----------------|---------------|--------------|
| forge (eager)     | **129.8 ms** | 58.7 ms     | 17.0 |
| pegainfer (graph) | 134.9 ms     | **48.9 ms** | 20.4 |

- **prefill: forge now matches/edges out pegainfer** (129.8 vs 134.9 ms) — the
  2× gap closed on 2026-05-27 (last-token logits + FA2-LSE) holds.
- **decode: forge 58.7 vs pegainfer 48.9 ms = 1.20×.** Real, not clock noise
  (forge reproduces 58.7 ms across sessions; clock steady). TPOT also depends on
  context length: short-prompt decode ~48 ms, prompt~1024 ~59 ms — only same
  workload is comparable.

**Decode root-cause — four directions ruled out:**
- **Not clock throttling** — SM steady 2411 MHz during decode.
- **Not kernel selection** — lm_head `[1,2560]×[2560,151936]` uses the same
  `cutlass_80 128x64` GEMM in an isolated probe (3.4 ms) and in production;
  cuBLASLt picks the same kernel (1.01×). The 12.6 ms in one nsys decode profile
  was an nsys/load-state artifact, not the steady-state kernel cost.
- **Not allocation** — `cuMemAllocAsync` median 368 ns, ~1452/step ≈ 0.5 ms.
- **Not CUDA graph** — profiling `--cuda-graph` decode: graph 51.6 vs eager
  48.5 ms/tok (**+3 ms, not the old 30 ms regression**). Graph cuts host overhead
  (~12.5→2.6 ms/step) but raises GPU-busy (36→49 ms, +13 ms): a one-shot
  `cuGraphLaunch` loses the host-GPU overlap eager gets from interleaving kernel
  submission with execution. `cuGraphLaunch` itself is only 128 µs;
  `AUTO_FREE_ON_LAUNCH` is not the culprit. This is a GB10/CUDA13 graph trait,
  not a forge bug — **graph is not the path to faster decode here**.

**What's left:** half of decode (proj GEMV ~29 ms/step) is the memory roofline
(reads ~8 GB of weights ÷ 273 GB/s) and is immovable. Closing the remaining
~13 ms vs pegainfer needs an **architectural decode pipeline** — overlapping
step N's host work (sample D2H + scheduler + FSM + detokenize) with step N+1's
GPU execution (exactly what eager doesn't do and what graph tried to replace but
failed on GB10). That's a large engine-core change, deferred.

## Reproduce

```bash
# forge
cargo build --release -p forge-server
./target/release/forge-server --model-path /path/to/qwen3-4b --port 8952
python3 scripts/bench_openai.py http://localhost:8952 qwen3-4b 256 1024 5

# pegainfer
/path/to/pegainfer --model-path /path/to/qwen3-4b --served-model-name qwen3-4b --port 8001
python3 scripts/bench_openai.py http://localhost:8001 qwen3-4b 256 1024 5

# vLLM (eager only — compiled mode hangs on GB10; lower mem-util to avoid OOM)
docker run -d --gpus all --network host --ipc=host --ulimit memlock=-1 \
  --ulimit stack=67108864 -v /path/to/qwen3-4b:/model --name vllm-bench \
  nvcr.io/nvidia/vllm:26.01-py3 vllm serve /model --served-model-name qwen3-4b \
  --port 8000 --enforce-eager --gpu-memory-utilization 0.6 --max-num-seqs 16
python3 scripts/bench_openai.py http://localhost:8000 qwen3-4b 256 1024 5
```
